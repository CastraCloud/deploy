# Changelog

## Unreleased

## 0.10.0 (20 November 2026)

**Before you upgrade from 0.9.0.** Take a backup as described in UPGRADING.md; the `migrate` step adds the new migrations on the first start. Then check these:

- A status page with its own host name stops being served on that host until you prove you control it: after the upgrade, add the DNS TXT record shown under the host name and press Check the record.
- `TRUST_PROXY=true` is refused at start-up. Leave `TRUST_PROXY` unset for the bundled web proxy (it then trusts one hop, or two when `CASTRA_TRUSTED_PROXIES` is set), or give a hop count or proxy addresses.
- Names in `CASTRA_OPERATORS` now only match people who sign in through the installation's own identity provider. With SAML set up from metadata alone (no `SAML_IDP_ENTITY_ID`), list operators as `issuer|subject`.
- Adding a member by username sends an email invitation unless the person signs in the same way as your organisation and belongs to no other organisation, so check outgoing email works.
- Mercury reports (SLA attainment, ageing, response times and the like) are now for desk staff only.
- With `MAIL_IN_TRUSTED_AUTHSERV` set, email that does not pass DMARC is never matched to staff.

- On a first install the app now waits quietly for the database migrations instead of logging errors until they finish. While it waits, the readiness check answers 503 with `waiting_for_migrations` and the liveness check stays healthy.
- Adding a member by username under Administration, Users now adds the person at once only when they sign in the same way as your organisation and belong to no other organisation. Anyone else is sent an email invitation, and joins (and their email address becomes visible to your admins) only when they open the link, signed in, within 14 days. The screen gives the same answer whatever the username, so names cannot be checked. Run the migrate step when you upgrade.
- An address added under Administration, Addresses is verified only when its DNS record is right and it also leads to your Castra over https; staff are handed a sign-in there only while it still does. An address nobody has proved no longer stops the organisation that does.
- Names in `CASTRA_OPERATORS` count only for people who signed in with the installation's own identity provider. To name one account exactly, write `issuer|subject` instead of a username.
- Directory sources and SCIM only match, update and switch off people their own organisation owns; a person who belongs to another organisation is left alone and SCIM answers 409 for that username.
- A suspended or read-only organisation is now also respected for personal API tokens used on the main address, SCIM and incoming webhooks.
- Email that opens a new ticket is no longer matched to staff by its From address alone. When `MAIL_IN_TRUSTED_AUTHSERV` is set, a message only counts as a staff member's if the mail server reports a passing DMARC result. Existing customers are still matched and answered as before, because many customers' domains publish no DMARC record. Mail from an unknown address that did not pass is opened from an unverified sender (a separate record that is never mailed) when your setting for unknown senders allows it, its description starts with a note saying so, and no acknowledgement or refusal is sent. Only the top-most `Authentication-Results` header from your trusted server is read, and results hidden in other headers or in an envelope sender are ignored. Without a trusted server configured nothing changes.
- Importers refuse a run that maps a source person to someone who is not a member of the organisation. Attachment names from the source are cleaned before they are stored, the source's credentials are dropped when a redirect changes host or scheme, answers from a source are read with a size limit (32 MB for data, your attachment limit for files), and an organisation can run only a few source calls and imports at once.
- Comments in a Confluence archive import are posted as the person who runs the import, marked "Imported comment, originally written by" the name in the file, because an archive can claim any author.
- A status page's own host name is only served after you prove you control it: save the host name, add the DNS TXT record shown under it (`_castra-verify.<host>`) and press Check the record. Hosts set before this need the check once. Castra's own address and hosts another organisation has verified cannot be used. Run the migrate step when you upgrade.
- `TRUST_PROXY` says how many proxies sit in front of the API (default 1, the bundled web proxy; 2 when `CASTRA_TRUSTED_PROXIES` is set) or lists their addresses, so a visitor can no longer choose the address that rate limits and audit entries record by writing `X-Forwarded-For`. IPv6 visitors are counted by their /64 network, and the public status page's limiter drops its oldest entries instead of refusing new visitors when it is full.
- The API no longer sends database error text to the browser: an unexpected failure answers with a short message and a request id that matches the server log. Database queries on the API stop after `DB_STATEMENT_TIMEOUT_MS` (default 30 seconds; 0 turns it off).
- Replies to chat commands in Mattermost and Rocket.Chat show an item's title as plain text, so Markdown and `@channel` in a title do nothing.
- Portal-only customers no longer count as staff, so an organisation-wide role no longer lets them look up staff by name.
- API tokens only reach attachments, reports and notifications of the products their scopes cover: a token with only Pages scopes cannot read work item or ticket files or reports, and notifications need a scope for every product. A service token limited to projects only gets the access given to it on those projects, not what an organisation-wide role gives every member.
- Asset questions in a request type can only point at schemas the person saving the form can read, and the schema list in the form editor shows only those. A service can only be linked to an asset object its editor can read. Approvers do not see answers to agent-only questions, and a "person" question on a portal request is held to the people the portal's picker offers.
- Link previews have their own list of private ranges, `LINK_PREVIEW_ALLOW_PRIVATE_CIDRS`, so a range opened for webhooks with `WEBHOOK_ALLOW_PRIVATE_CIDRS` no longer opens it for previews. The NAT64 local-use range (`64:ff9b:1::/48`) is refused like other private ranges.
- The web proxy refuses the identity provider's admin console and master realm however the address is written (for example with `;` parameters, doubled slashes or dot segments).
- Dragging a card to another column on a board or in the backlog no longer makes it jump back to its old column for a moment before it appears in the new one.
- Word, Excel, PowerPoint and OpenDocument attachments can be previewed in the browser. Castra converts them to PDF with Gotenberg (MIT licence, LibreOffice inside) and opens the PDF in the same viewer as other PDFs, with a Download original button. While the preview is being made the dialog says so and updates by itself; if it cannot be made, or previews are off, it says "No preview available". It works in the agent app and in the portal, in English, German and French, for the newest version and for older ones, and only for people who can read the file. Previews are off until you set `PREVIEW_URL` (`previews.mode` in Helm; `install.sh` asks, and the default is no). The bundled converter is a large image with its own Compose profile `previews` (the `full` profile includes it), no published port and no route to the internet; use `compose.external-previews.yml` for your own. Files over `PREVIEW_MAX_BYTES` (20 MB) are not converted. Run the migrate step when you upgrade. See Office previews in the README.
- Link previews. A link to another site that you paste on a line of its own in a page, a comment or a ticket reply now shows as a small card with the site, title and a short description, for agents and for requesters on the portal. Castra's server fetches the page (not the reader's browser), uses the site's oEmbed or its Open Graph tags, refuses private network addresses, reads only the start of the page and keeps the answer for a day for the whole organisation. Thumbnails and site icons are off by default, because showing them means each reader's browser contacts the other site. Under Administration, Email and tools, Link previews, an admin can turn previews off, allow thumbnails and list domains that are never fetched. PDF and Word exports print the link with its title when it is already known. Run the migrate step when you upgrade. See Link previews in the README.
- Service catalogue. Under Mercury, Settings, Request types and forms, Services, a desk lists the services it offers, each with a short description, a Markdown description, an owner (a person or a team; the portal names a team, and names a person only when the desk turns on "Show named people as service owners on the portal" at the top of the Services page), an optional link to an object in the asset inventory, an order, and whether requesters see it. Request types can belong to a service, and a ticket takes the service of its request type when it is raised; agents can change it on the ticket. Queues have a Service column and filter, `service = "Email"` works in the filter language, and custom reports can be split by service. On the portal, Browse services on the home page shows a card for each service, with its status when it is linked to an asset on the status page, and opens a page with the description, its request types and related help articles. Service names and descriptions can be translated with the desk's other languages. Run the migrate step when you upgrade.

- Live docs. A library can now publish every edit as it is made: under Library settings, Publishing, choose Live docs (no publish step) instead of Pages need review or Publish when the author chooses. On a live doc readers always see the latest saved text, with a Live doc label and who last edited it and when, and there is no Submit for review or Publish button. An editor can switch a single page between live and regular from the page itself; switching to regular keeps the current text published. History shows a burst of saves as one entry, and people who watch a live doc hear about its edits at most once an hour. Restrictions, labels, comments and the page tree work as before. A page whose library requires review cannot be a live doc. Run the migrate step when you upgrade. See Live docs in the README.
- Menus are reorganised. Each product menu now shows the work, with one Settings link (the gear) that opens a settings menu for that service desk, project or library, grouped under headings and with a Back link at the top. Administration is grouped under People and access, Portal, Email and tools, Notifications, Data and Installation, and Personal Settings keeps only personal items with a single Administration link for organisation admins. Business hours moved to Administration, Installation. Every page keeps its address.
- The portal's sign-in page shows the organisation's branding before anyone signs in. On the portal's own address the page is split in two: the left half carries the logo, name, heading and introduction from Administration, Portal look, in the portal's accent colour (with dark text when the colour is too light for white), and the right half has the language menu, the identity provider button, the emailed link form and a small staff sign-in link. After the link is sent the page says to check your email, offers Send again after 60 seconds, and lets people use a different address. Only the display fields (name, heading, introduction, logo, accent colour and languages) are public, and only on a portal address.

- Local groups. Under Administration, Groups, organisation admins can create, rename and delete groups of their own and add and remove their members, picking from staff who can sign in (never switched-off people or portal-only customers). Each group shows its source, member count and where it is used, with the members searchable. Groups that come from your identity provider, SCIM or a directory stay read-only. Deleting a group that is in use lists where it is used and, once confirmed, removes it from those roles and schemes. Every change is in the audit log. See Local groups in the README.
- Staff can sign in with SAML 2.0, for estates that only have ADFS or another SAML identity provider. Set `SAML_IDP_METADATA_URL` and `SAML_IDP_ENTITY_ID` (`signIn.saml` in Helm, and `install.sh` asks: choose your own provider, then SAML) instead of the `OIDC_*` settings; an installation uses one or the other and will not start with both. Give your provider `<your address>/auth/saml/metadata`. Castra accepts only signed responses from the certificates in the provider's metadata, and checks audience, address, timing and the request, once each. Attribute names default to what ADFS and Entra ID send and can be changed; groups, required groups, first administrators and sign-in to portal host names work as with OIDC. Single logout is not supported: signing out ends the Castra session only. See Sign-in in the README for ADFS and Entra ID setup.
- A System page for the people who run the installation. Name them in `CASTRA_OPERATORS` (`signIn.operators` in Helm); bootstrap admins can open it too, organisation admins cannot unless they are listed. Operators find System in the account menu (`/system`): health checks, version and uptime, licence state, database migrations applied and pending, database size and largest tables, when each background loop last ran, queues and failures from the last 24 hours, and every organisation's members, staff, last activity and storage. Operators can retry failed webhook and email jobs, record usage counts now and run an identity source now; each action is written to the audit log of the organisations it touched. Run the migrate step when you upgrade.

- A restore drill. `compose/restore-drill.sh IMAGE_TAG` (`scripts/restore-drill.sh` in the repository) starts a throwaway stack, loads demo data, runs `backup.sh`, destroys the stack, restores it with `restore.sh` and checks that row counts, attachment checksums, the audit chain, a page's versions and a ticket's comments all came back, then prints PASS or FAIL. It uses its own project name and removes only what it made; `--plan` shows the steps without running Docker. See Backups in the README.
- A desk, or the organisation default, can send its customer email through a Microsoft 365 or Google Workspace mailbox without an SMTP password. Register an OAuth app with each provider once (see Desk email in the README for the steps and the redirect URI `<CASTRA_PUBLIC_URL>/api/v1/mail-oauth/callback`), set `MAIL_OAUTH_MICROSOFT_CLIENT_ID`, `MAIL_OAUTH_MICROSOFT_CLIENT_SECRET`, `MAIL_OAUTH_MICROSOFT_TENANT`, `MAIL_OAUTH_GOOGLE_CLIENT_ID` and `MAIL_OAUTH_GOOGLE_CLIENT_SECRET` (`email.oauth` in Helm), and Connect Microsoft 365 and Connect Google appear in the desk's Outgoing email section. The signed-in mailbox becomes the From address, a revoked connection shows Reconnect, and mail from that desk never falls back to another relay. Without the settings nothing changes and the buttons are hidden.
- French is now offered beside English and German. The requester portal and its customer emails are fully in French, and a desk can add French (Français) to its languages. In the agent app, choose Français in the account menu: every screen is translated.
- The requester portal can have a host name of its own. Set `CASTRA_PORTAL_DOMAIN` (for example `help.example.com`; `portal.host` in Helm, and `install.sh` asks) and the portal is served at the root of that name for your first organisation, with a certificate in every TLS mode. The portal still works at `/portal/`. Under Administration, Addresses an organisation can add more names, which are used once a DNS TXT record verifies them. A sign-in on one host name never works on another.
- Customers can sign in to the portal with an emailed link. They enter their email address and get a link that works once, for 15 minutes, on that portal address only; the page gives the same answer whether or not the address is known, and requests are limited per address and per client. The email is in the person's language, or the one the portal page was in. Under Administration, Portal access you choose who may sign up (anyone, people from listed email domains who can join a customer organisation, or invited people only) and invite people by email; admins and agents can invite through the API. Customers have portal-only accounts that can never hold a staff role. Convert one to staff under Portal access, and the person then signs in through staff sign-in with the same address. Accounts made from inbound mail are portal-only customers too.
- An organisation can let people sign in to its portal with its own identity provider, Microsoft Entra ID or any OpenID Connect provider, beside the emailed link or instead of it. Under Administration, Portal access enter the issuer, client ID and secret, test the connection, and register the redirect URI the page shows. Customers get a "Sign in with" button on the portal sign-in page and are matched to, or given, a portal-only account by their verified email address. You can limit it to listed email domains and pick the customer organisation new people join. Staff are always sent to staff sign-in. See the README for Entra ID setup.
- Staff can use the portal at its own address: they sign in with their normal staff sign-in and see what a requester sees, their own requests and raising a request, never the agent tools.

- Service desks can send and receive email their own way. Under Mercury, Settings, a desk can now save its own mail relay (host, port, connection security, user name and password) and a From and optional Reply-To address, and customer email from that desk (replies, updates, surveys, automatic answers, portal sign-in links and invitations, and template test sends) goes out through it, while agent and internal notifications keep using the server's relay. Send test email shows what the relay answered, passwords are stored encrypted and never shown again, and the screen explains the SPF, DKIM and DMARC records your From domain needs. An organisation default is under Administration, Desk email. Incoming mail works by forwarding only: each desk shows a Castra address to forward its support mailbox to, and Check forwarding sends a code to the support address and confirms when it comes back through the forward. Castra never signs in to a customer's mailbox, and mail that claims to come from a desk's own address never opens a ticket. The server's own SMTP, IMAP and webhook settings are unchanged and remain the default. See Desk email in the README.
- French is now offered beside English and German. The requester portal and its customer emails are fully in French, and a desk can add French (Français) to its languages. In the agent app, choose Français in the account menu; the top bar, navigation, account settings, home page and attachments are in French now, and the other screens follow, showing English until then.
- The Castra Licence is now accepted before Castra is used. `install.sh` shows a short notice and asks you to type `yes` (answers files take `ACCEPT_LICENCE=yes`, or pass `--accept-licence`), and the first administrator to sign in is asked to read and accept the licence in the app. Until then nobody else can use Castra, and the requester portal says it is not ready yet. The accepted version, who accepted it and when are under Administration, Licence, and it is asked again if the text changes. The licence is also in the images as `/LICENSE`. Installations covered by other terms can set `CASTRA_LICENCE_ACCEPTANCE=off` (`licence.acceptance: off` in Helm).
- Fixed: a change could occasionally look undone straight after saving, for example a deleted item still appearing when the list was opened at once.

## 0.9.0 (14 November 2026)

The first public release.

- You can limit sign-in to certain groups. Set `OIDC_REQUIRED_GROUPS` (or `signIn.oidc.requiredGroups` in Helm, or answer the new `install.sh` question) to a comma-separated list of group names, and anyone whose token carries none of them in the groups claim is refused with a message to ask their administrator, and no account is made. The check uses the token only. Unset, nothing changes.
- Draw.io can run on a host name of its own instead of a second port. Set `CASTRA_DRAWIO_DOMAIN` (for example `castra-diagrams.example.com`) and the web proxy serves the editor on the same ports as Castra, with its own certificate in the self-signed, acme and files TLS modes (files mode takes one certificate covering both names, or `CASTRA_TLS_DRAWIO_CERT` and `CASTRA_TLS_DRAWIO_KEY`). `install.sh` now suggests a name when you give it a domain. Existing installs keep the port until you set the variable; see Upgrading for the steps. The Helm chart already used a host (`drawio.host`).
- People who have been switched off by an identity source no longer turn up when you pick someone: assignee and reporter lists, mentions, project lead and default assignee, Add access, dashboard editors, incident people, scheme editors, automation actions and the portal's colleague and raise-on-behalf lists all leave them out. They still show by name on items and history they already appear on. Staff pickers for project lead, default assignee, dashboard editors and incident people now also offer a From the directory group when an identity source has search on; choosing someone creates their account. The portal never offers a directory.
- Identity sources can be SCIM 2.0. Microsoft Entra ID, Okta and other providers push people and groups to Castra at `/api/scim/v2` with a bearer token you make under Administration, Identity sources, Add a SCIM source. People appear straight away and join their account when they sign in (by verified work email, userName or externalId); deactivating or deleting a person switches them off in your organisation, and pushing them again switches them back on. Groups the provider pushes stay in step and cannot be edited by hand. Tokens are shown once, rotate with two valid at once, can be revoked, and only reach their own source. A SCIM source can be paired with a Keycloak source, which then refreshes a person at sign-in and finds people for the Add access box. The screen shows the base URL, last request and recent errors, and SCIM sources can be set in the identity file. See Identity sources in the README.
- Usage history. Administration, Usage shows how many people use Castra: members, organisation admins, people who signed in during the last 30 and 7 days, staff in Minerva, Caelus and Mercury, portal customers and switched-off accounts. Castra saves the numbers once a day, so you get today's figures, a chart of the last 90 days or the last year, a daily table and Download CSV. History starts the day you upgrade.
- Identity sources. Administration, Identity sources connects Castra to your Keycloak. It reads people and groups on a schedule, so people appear in pickers before they first sign in (and are matched to their account when they do), groups from Keycloak are kept up to date and cannot be edited by hand, and people who are disabled or have left Keycloak are switched off: their sessions end, personal API tokens and push subscriptions stop, they cannot sign in, and what they wrote stays. A source is tried with Test connection and Preview, which changes nothing, before it is switched on. A run that would switch off more than 10 percent of a source's people (you can change the figure) stops until an admin confirms it. A source can also refresh a person's groups when they sign in, and offer people from Keycloak in the Add access person box before they have an account. Purge former people removes the personal data of people switched off for 90 days or more, after a preview and a typed confirmation, and keeps what they wrote under "Former user" and a number. Sources can instead be set from a file with `CASTRA_IDENTITY_CONFIG`; the screen is then read-only. See Identity sources in the README.
- Identity sources can now read people from any JSON API. Administration, Identity sources, Add an HTTP source takes the address of the list, how to sign in (bearer token, user name and password, a custom header or OAuth client credentials) and how it is paged (page, offset, cursor or the Link header), then which part of each record is the id, email, name, whether they are active and their groups. Paste a sample answer and each field is checked as you type; Test connection shows the first records from the real API and any problems. It can also look one person up at sign-in and search people who have not signed in yet, and be set from the identity file. See Identity sources in the README.
- Four more Caelus page macros that read live data for each reader. `::minerva-report{project="PAY" type=burndown sprint="Sprint 4"}` draws a sprint burndown (or `type=velocity` for the last closed sprints). `::minerva-board{project="PAY" board="Team board"}` shows a read-only snapshot of a board with a link to the live one. `::mercury-sla{desk="HELP" period=30d}` shows SLA goals met, missed and at risk for a service desk, for its agents only. `::kb-article{desk="HELP" article="Reset a password"}` shows a published knowledge base article in a page, with a link to the portal for requesters and to Caelus for agents. All four print in PDF and Word, are offered in the macro list with help text, and show "not available" instead of anything the reader cannot open; secured issues are not counted. Confluence imports now convert Jira pie and created-against-resolved charts to Minerva charts.
- New Caelus page macros. `::minerva-release{project="PAY" version="1.4"}` shows how far a Minerva version is, with its release date, released or not, and a progress bar of items to do, in progress and done. `::content-by-label{labels="a,b" as=table}` lists matching pages as a table with library, last update, who by and labels. `::change-history` lists a page's published versions with who, when and the version comment. `:date[2026-11-14]` is a date chip in each reader's language, shown as overdue when written `:date[...]{task}` in a task list item and past; the slash menu item Date inserts today. All print in PDF and Word, and none shows items, pages or libraries the reader cannot open. Confluence imports now convert `change-history`, the content report table and dates.
- Long lists show 10,000+ instead of an exact total when there are more than 10,000 matches, in the issue navigator, the backlog, desk ticket queues and the header search.
- The agent app can be shown in German. Choose a language from the account menu (Language) or under Settings, Language; it is saved to your profile, so it follows you to other devices, and with nothing chosen your browser's language is used, then English. Dates, times and numbers follow it. Every screen is translated, including the Minerva, Mercury and Caelus settings, reports, editors, import and export, search, dashboards, API tokens, automation, assets and the Administration screens. Names and messages that come from the server, and a few built-in names saved as data, stay in English. To confirm a bulk page delete in German, type löschen (delete still works).
- Castra can be installed on a phone or computer. Use Install app (or Add to Home Screen) in your browser for the agent app and, separately, for the portal, which takes its name from the portal heading. Items, tickets and pages you opened recently can be read offline, with a banner showing when the saved copy was made; changes cannot be made offline and say so. Saved copies are kept per person on that browser and are cleared when you sign out. A bar offers Reload when a new version is ready. Push notifications are new too, and off until an administrator sets `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY` and `WEB_PUSH_CONTACT` (the install script can make the keys; the Helm chart has a `push` block). Then each person turns them on per device under Settings, Notifications, Push notifications on this device. They follow your notification choices, show only the event's name and a link, and are removed when you sign out of that browser. On iPhone and iPad, add the app to the Home Screen first.
- Object storage can use an AWS role instead of fixed keys. Set `S3_CREDENTIALS=aws-default` (and leave `S3_ACCESS_KEY` and `S3_SECRET_KEY` unset) and Castra uses an EC2 instance role, an ECS task role, EKS pod identity or EKS IRSA, refreshing the credentials itself. The default, `keys`, is unchanged. In the Helm chart set `storage.s3.credentials: aws-default` and annotate the service account for IRSA; the Docker Compose file no longer insists on the two S3 keys being set, so check `.env` still has them if you use the bundled SeaweedFS.
- On call for service desks. Under On call in a desk's menu, a service manager sets up schedules for a desk team: rotations that are daily, weekly or a number of days long, with a hand-over time and time zone, an ordered list of people, layers (for example one for weekdays and one for weekends) and cover for a period. The page shows who is on call now and next, the next four weeks, and a calendar feed with only your own shifts that you can add to your calendar app (the key is shown once and can be revoked). Escalation policies list the steps: the person on call for a schedule, a named person or a group, and how many minutes to wait for an acknowledgement before the next step, with the whole policy repeating up to a number of times.
- Pages. A page starts when a major incident is declared or made major, when an SLA target is missed on a desk that chose a policy for it, from the new "Page on-call" automation action, or by hand from a ticket. It tells people in the app, by an email that is sent at once, in the desk's chat channels that choose "On-call page triggered", and with a new `page.triggered` webhook event, so you can connect your own text or phone service. Acknowledge in the app, from the link in the email, or with `/castra ack <code>` in chat. Acknowledging stops escalation, and resolving the ticket resolves its pages. Incident timelines show the paging. Reports show pages per week, time to acknowledge and out-of-hours pages per person. Choose which policy each desk uses under On call, Settings.
- Large installs are faster. Searches, boards, backlogs, reports, dashboards, the home page, library search, the audit log and smart links were measured with 100,000 items, 50,000 tickets and 20,000 pages and several of them got 10 to 1,000 times quicker (some took seconds or minutes before). The upgrade adds indexes and rebuilds a search column on page versions, which can take a minute or two on a big database; installs with very large tables can create the indexes by hand first (see `docs/performance-2026-11.md`). Lists in search, the project item list, the backlog and desk ticket lists now count matches only up to 10,000: below that nothing changes, above it the total shows 10,000 and the response says `totalCapped`.
- Library search, the header search and the home page are faster again on very large installs (20,000 pages): they now work out which pages you may open in the database instead of loading every page first. Who can see what is unchanged.
- Tighter limits on what the web proxy lets a page frame. The default is now Castra itself and your Draw.io editor, where it used to be any https site. If pages embed other sites, set `CASTRA_FRAME_SRC` to the line shown under Administration, Embedded sites (it now starts with the Draw.io address). The Helm chart has a new `web.frameSrc` value for the same purpose.
- Signed incoming webhooks now need a timestamp. Send `X-Castra-Timestamp` (Unix seconds) and sign `<timestamp>.<body>` instead of the body alone, or write the header as `t=<timestamp>,v1=<signature>`. Requests more than 5 minutes from the server clock, and a signature seen twice, are refused. The Incoming webhooks screen and the README show the format and an example. Webhooks with no signature work as before and are only as safe as their secret address. Update senders that sign the body alone before upgrading.
- Retention runs now list what they removed. Each applied run adds `retention.removed` entries to the audit log for each kind of data, with the keys of tickets and items or the ids of everything else (up to 1,000 per entry), next to the existing counts.
- Connecting a chat account needs a code typed in the chat. After opening the link from chat and pressing Connect, Castra shows a one-time code, and the same chat user types `/castra link <code>` within 10 minutes. Links handed out before the upgrade stop working; ask chat for a new one.
- Minerva has voting, a calendar and a list view. People who can see an item can vote for it, or take the vote back, from its page, and see how many votes it has and who voted; counts show on cards and in the backlog. - Incoming webhooks, retention policies, audit log streaming and monitoring. **Incoming webhooks:** a project or desk admin gives another system a private address (shown once, rotatable) that either runs an automation rule or creates an item or ticket from fields of the JSON it sends. - MQL has more to ask.
